## 1 · Deploy the two functions

Deploy configuration matters more here than usual, because the two functions sit on
opposite sides of the trust boundary.

```bash
cd crm
supabase functions deploy wa-webhook --no-verify-jwt --project-ref zyvhcnhablkgbsgtljma
supabase functions deploy wa-send                    --project-ref zyvhcnhablkgbsgtljma
```

Or, via the Supabase MCP `deploy_edge_function`, with the files `index.ts` and `core.ts`
from each directory:

| Function | `verify_jwt` | Why |
|---|---|---|
| `wa-webhook` | **`false`** | Meta's servers call this URL. They have no Supabase JWT and never will, so the gateway's check cannot be the authentication. The function implements its own, and it is the stronger of the two: the `GET` handshake is guarded by `WA_VERIFY_TOKEN`, and every `POST` is guarded by `X-Hub-Signature-256` — HMAC-SHA256 over the **raw** body under `WA_APP_SECRET`, compared in constant time. Nothing is read out of the body before that check passes. The same posture as `ics-feed` (10 §4), for the same reason. |
| `wa-send` | **`true`** | The one outbound door. The Supabase client is built from the **caller's** `Authorization` header, never the service-role key, so every message is attributable to a signed-in human and is held to the 11 §1 policies. That absence of a service-role path is how I-10 ("automations create tasks and flags, humans send messages") is *enforced* rather than promised. |

`core.ts` in each directory is a generated byte-identical mirror of
`src/features/whatsapp/core.ts` (`tests/wa-mirror.test.ts` fails if one drifts). Regenerate with:

```bash
for fn in wa-webhook wa-send; do
  { printf '// GENERATED MIRROR — do not edit.\n// Source: crm/src/features/whatsapp/core.ts. The Deno edge runtime cannot reach\n// into src/, so each function carries a byte-identical copy under this header.\n// tests/wa-mirror.test.ts fails the build the moment one drifts.\n'
    cat src/features/whatsapp/core.ts
  } > supabase/functions/$fn/core.ts
done
```

## 2 · Verify the unset state (do this immediately after deploying)

These three calls are the acceptance evidence for "unconfigured is a supported state".
With no secrets set they should answer exactly as below.

```bash
FN=https://zyvhcnhablkgbsgtljma.supabase.co/functions/v1
ANON=sb_publishable_TUrSdmuJIrQ-YJCH5zDkJg_QDdFCZw-   # publishable, safe to paste
```

**a · the webhook handshake, with no `WA_VERIFY_TOKEN`**

```bash
curl -si "$FN/wa-webhook?hub.mode=subscribe&hub.verify_token=anything&hub.challenge=1158201444" | head -20
# expect: HTTP/2 503
#         {"error":"wa_unconfigured","message":"WA_VERIFY_TOKEN is not set."}
```

**b · an unsigned webhook POST, with no `WA_APP_SECRET`**

```bash
curl -si -X POST "$FN/wa-webhook" -H 'content-type: application/json' -d '{}' | head -20
# expect: HTTP/2 503
#         {"error":"wa_unconfigured","message":"WA_APP_SECRET is not set."}
#
# This is the documented unset-env behaviour: the secret check comes BEFORE the
# signature check, so an admin mid-setup is told what is missing instead of
# being handed a 401 that looks like Meta's fault. Once WA_APP_SECRET is set,
# this same call answers 401 {"error":"bad_signature"}.
```

**c · `wa-send` with a valid caller JWT, with no `WA_ACCESS_TOKEN` / `WA_PHONE_NUMBER_ID`**

```bash
JWT=$(curl -s "https://zyvhcnhablkgbsgtljma.supabase.co/auth/v1/token?grant_type=password" \
  -H "apikey: $ANON" -H 'content-type: application/json' \
  -d '{"email":"admin@demo.test","password":"YeshivaCrm-demo1"}' \
  | python3 -c 'import sys,json; print(json.load(sys.stdin)["access_token"])')

curl -si -X POST "$FN/wa-send" \
  -H "apikey: $ANON" -H "Authorization: Bearer $JWT" \
  -H 'content-type: application/json' \
  -d '{"action":"status"}' | head -20
# expect: HTTP/2 503
#         {"error":"wa_unconfigured","message":"WhatsApp Business is not connected. …"}
```

**d · the window rule, once the tokens *are* set** (the check that matters)

```bash
# A conversation whose last_inbound_at is older than 24 hours, free-form body:
curl -si -X POST "$FN/wa-send" \
  -H "apikey: $ANON" -H "Authorization: Bearer $JWT" \
  -H 'content-type: application/json' \
  -d '{"conversation_id":"<the closed demo conversation id>","body":"hello"}' | head -20
# expect: HTTP/2 409
#         {"error":"window_closed","message":"The 24-hour customer-service window has closed. …"}
#
# The composer never offers this; the 409 is what stops a stale tab, a replayed
# request or a hand-rolled curl from doing what the composer refused.
```

## 3 · Secrets (Supabase → Edge Functions → Secrets, or `supabase secrets set`)

| Secret | What it is | Where in Meta |
|---|---|---|
| `WA_ACCESS_TOKEN` | system-user access token the Cloud API is called with | Business Manager → Business settings → Users → System users → **Generate token** (assign the WhatsApp app, scopes `whatsapp_business_messaging` + `whatsapp_business_management`) |
| `WA_PHONE_NUMBER_ID` | which business number sends | Meta app → WhatsApp → **API setup** → “Phone number ID” |
| `WA_VERIFY_TOKEN` | shared string proving we own the webhook URL | invent one (e.g. `openssl rand -hex 24`); paste the same value into the app's Webhook config |
| `WA_APP_SECRET` | signs every webhook delivery | Meta app → App settings → **Basic** → “App secret” |
| `WA_BUSINESS_ACCOUNT_ID` | only needed by “Sync templates” | Meta app → WhatsApp → API setup → “WhatsApp Business Account ID” |

```bash
supabase secrets set --project-ref zyvhcnhablkgbsgtljma \
  WA_ACCESS_TOKEN=… WA_PHONE_NUMBER_ID=… WA_VERIFY_TOKEN=… WA_APP_SECRET=… WA_BUSINESS_ACCOUNT_ID=…
```

Nothing above is ever sent to the browser. Settings → WhatsApp shows each one as set/not-set
by **probing** the deployed functions (503 vs 403/401/200) — a screen that claimed to read a
secret would be lying.

## 4 · Meta app configuration

1. Meta app → **WhatsApp → Configuration → Webhook → Edit**
   - **Callback URL**: `https://zyvhcnhablkgbsgtljma.supabase.co/functions/v1/wa-webhook`
   - **Verify token**: the value stored as `WA_VERIFY_TOKEN`
   - Press **Verify and save**. Meta issues the `GET` above; the function echoes
     `hub.challenge` verbatim as `text/plain` only when the token matches in constant time.
     A 503 here means the secret is not set yet; a 403 means the token does not match.
2. **Subscribe** the app to the **`messages`** field (this carries both inbound messages and
   delivery receipts). Nothing else is needed.
3. Business verification and a display-name review must be complete before the number can
   message people outside your test list — that is Meta's process, not ours.
4. Templates are written and approved in **Business Manager → WhatsApp Manager → Message
   templates**. Then press **Sync templates** in Settings → WhatsApp, which runs
   `GET /<WA_BUSINESS_ACCOUNT_ID>/message_templates` server-side and mirrors the catalogue
   into `wa_templates`. This app never creates, edits or approves a template.

## 6 · The live screenshot

Sandboxed Chromium cannot open TLS to `*.supabase.co`, so the browser talks to the relay:

```bash
cd crm
NODE_USE_ENV_PROXY=1 node e2e/supabase-relay.mjs --port 5433 &
VITE_SUPABASE_URL=http://127.0.0.1:5433 npx vite --port 5198 --strictPort --host &
E2E_BASE_URL=http://localhost:5198 E2E_SHOT_SUFFIX=live E2E_LIVE=1 node e2e/c2-shots.mjs
# writes e2e/shots/c2-{conversations,thread,window-closed}-live.png
```

`E2E_LIVE=1` signs in as `admin@demo.test` on the app's own login page first (same origin,
same localStorage), because the pane is shot through `e2e/wa-harness.html` — a development
page that mounts the pane directly while the Comms shell is being built in parallel. The pane
also registers itself with that shell (`registerCommsChannel`, side-effect import in
`src/main.tsx`), so it appears at `/comms` the moment the rail lands, with no change here.

The offline equivalent, which needs no credentials at all:

```bash
node e2e/wa-fixture-server.mjs --port 5298 &
VITE_SUPABASE_URL=http://127.0.0.1:5298 VITE_SUPABASE_ANON_KEY=fixture npx vite --port 5198 --strictPort --host &
```
